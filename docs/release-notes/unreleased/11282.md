# New Features

## Functional Enhancements

* Introduced a [`RouteOrigin`
  interface](https://github.com/lightningnetwork/lnd/pull/10764) that
  generalizes where routes can originate from. The pathfinder previously
  terminated at a single concrete source vertex; `RouteOrigin` replaces this
  with a predicate so the backward search can terminate at any vertex in a
  caller-provided set, selecting whichever provides the cheapest path. The
  default `singleOrigin` preserves existing behavior for all callers. This is
  the source-end counterpart to `AdditionalEdge`, which extends the graph at
  the destination end via route hints.

* The switch's attempt store records an attempt as `PENDING` [before it is
  dispatched](https://github.com/lightningnetwork/lnd/pull/10049), a durable
  write of intent that gives remote clients "at most once" processing of HTLC
  dispatch requests through the `switchrpc.SendOnion` RPC. The flow for
  dispatching local payments is unchanged.

* Added a new switchrpc RPC sub-system
  ([#9489](https://github.com/lightningnetwork/lnd/pull/9489),
  [#11282](https://github.com/lightningnetwork/lnd/pull/11282))
  with `SendOnion`, `BuildOnion`, `TrackOnion` and `DeleteAttempts`
  endpoints. This allows the daemon to offload path-finding, onion
  construction and payment life-cycle management to an external entity and
  instead accept onion payments for direct delivery to the network. The
  compilation of the server is hidden behind the non-default `switchrpc` build
  tag. lnd's own `ChannelRouter` and any number of `switchrpc` clients can
  dispatch payments on the same node at the same time.

* The `SendOnion` RPC is [idempotent](https://github.com/lightningnetwork/lnd/pull/10473),
  so an external payment orchestrator (such as a remote `ChannelRouter`) can
  safely retry a request after a network timeout or an ambiguous outcome
  without risking a duplicate payment. Each attempt is named by an
  `AttemptKey`, 16 to 64 opaque bytes chosen by the client, unique among all
  clients of the node and never reused. A retry with the same key and the same
  request is acknowledged rather than dispatched again. A request under a
  registered key that differs in a field defining the HTLC is answered
  `Mismatch` and nothing is dispatched.

* The `switchrpc.SendOnion` RPC reports what happened to an attempt in its
  response ([#10545](https://github.com/lightningnetwork/lnd/pull/10545),
  [#11546](https://github.com/lightningnetwork/lnd/pull/11546)).
  `SendOnionResponse` carries exactly one of `Accepted` (the switch owns the
  attempt; track it with `TrackOnion`), `Rejected` (the HTLC never left the
  node; it carries the BOLT 4 wire failure, and the caller may route a new
  attempt), `Ambiguous` (retry the same attempt key), or `Mismatch` (the key
  is registered for a different request; stop and alert). A gRPC error means
  only that the call itself failed.

* The `switchrpc.TrackOnion` RPC
  ([#10472](https://github.com/lightningnetwork/lnd/pull/10472)) waits for
  the result of an attempt named by its key. `TrackOnionResponse` uses a
  top-level `oneof` that holds either a `preimage` (for success) or structured
  `FailureDetails` (for a payment failure). Failures of the query itself, such
  as an unknown key, are reported with standard gRPC status codes.

* The [`switchrpc.DeleteAttempts`](https://github.com/lightningnetwork/lnd/pull/10602)
  RPC lets an external router remove terminal (settled or failed) attempts.
  It accepts a batch of attempt keys and reports, per key, whether the attempt
  was deleted, is still pending (in-flight), was not found, or could not be
  processed. Deleting an attempt makes the server forget its key, so a later
  `SendOnion` with the same key dispatches a new HTLC. Clients must only
  delete an attempt after durably recording its final result, and must never
  send a deleted key again.

* The `ChannelRouter` now supports a [configurable attempt reconciliation
  hook](https://github.com/lightningnetwork/lnd/pull/10621) that runs for each
  in-flight HTLC attempt during startup, before result collection begins. This
  enables write-first crash recovery for deployments where the router and switch
  run in separate processes (e.g. a remote `ChannelRouter` dispatching via
  `switchrpc.SendOnion`). The callback lets the caller confirm dispatch status by
  idempotently re-submitting each attempt, resolving the ambiguity that arises
  when a crash occurs between persisting an attempt and receiving the switch's
  acknowledgement. The default is a no-op, so existing single-process lnd
  deployments are unaffected.

# Improvements

## RPC Updates

* [Add `source_pub_key` to `Route` proto message](https://github.com/lightningnetwork/lnd/pull/9153)
  so that routes can be constructed and unmarshalled from the perspective of
  different nodes. Defaults to the node's own public key.
